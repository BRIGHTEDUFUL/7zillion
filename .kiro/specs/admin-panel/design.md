# Design Document — Admin Panel

## Overview

The admin panel introduces a protected management interface into the Seven Zillions application. The current site is a static-data TanStack Start app deployed on Cloudflare Workers: all content lives in `src/data/site.ts`, there is no database, no backend API, and no authentication. This feature replaces the static data layer with a live Content_Store (Cloudflare KV or D1), adds a server-side Auth_Service and Content_API implemented as TanStack Start server functions, and builds the `/admin` route subtree as a React SPA shell that reads from and writes to those server functions.

The public site continues to work as today — the same route files, the same component tree — except that instead of importing from `src/data/site.ts` they call server functions that read from the Content_Store at request time, satisfying the no-cache-between-store-and-response requirement.

### Key Design Decisions

**KV vs D1.** Cloudflare KV is an eventually-consistent key-value store; D1 is a strongly-consistent SQLite-compatible database. For this application the content collections are small (tens of items per type) and admin writes are infrequent. Both storage options are viable. This design treats them as interchangeable behind a storage adapter interface (`ContentStore`), and recommends **D1** as the default because it supports transactions, atomic slug-uniqueness checks, and ordered queries natively, while the implementation effort difference is minimal. The adapter pattern means the decision can be reversed without touching the Content_API or Admin_Panel layers.

**Server functions vs dedicated API routes.** TanStack Start server functions (`createServerFn`) run on the Cloudflare Worker and share the same request context. They are the right primitive here: they are type-safe end-to-end, they colocate the API contract with the call site, and they avoid the overhead of setting up a separate HTTP API layer. All Content_API and Auth_Service operations are implemented as server functions.

**Authentication strategy.** The requirements specify username+password authentication with an HTTP-only session cookie. No external identity provider is required. A single set of admin credentials (stored as environment variables on the Worker) is validated server-side. Sessions are stored in Cloudflare KV (a lightweight "sessions" namespace separate from content storage) with a 8-hour TTL. A `crypto.randomUUID()` session token is the cookie value; the server looks it up on every protected request.

**Image uploads.** Images are uploaded directly from the browser to Cloudflare R2 using a pre-signed PUT URL generated by a server function. The browser never sends the binary file to the Worker; only the metadata (filename, MIME type) passes through the server function to generate the signed URL. After upload, the R2 public URL is sent back to the form and stored alongside the content item.

**No-cache data reading.** Public route loaders (`loader` on the TanStack Router route definition) call server functions that read from the Content_Store directly. Because TanStack Start's `loader` runs server-side on every SSR request and the results are not cached at the CDN edge (Cloudflare Workers bypass edge cache by default for Worker routes), every page render reflects the current store state.

The Worker handles all requests. Public routes load data from D1 via the Content_API on every SSR render. Admin routes are protected by a session middleware check at the router level. The Auth_Service uses KV for session tokens and rate-limit counters (KV is appropriate here because these are short-lived scalar values, not relational data). Images bypass the Worker binary body by using R2 pre-signed PUT URLs.

## Components and Interfaces

### 1. Storage Adapter (`src/lib/content-store.ts`)

Abstracts D1 (default) or KV behind a typed interface so the Content_API is not coupled to a specific Cloudflare binding.

```ts
export interface ContentStore {
  // Company
  getCompany(): Promise<Company>;
  setCompany(data: Company): Promise<void>;

  // Generic collection CRUD used by all content types
  listItems<T>(collection: CollectionName): Promise<T[]>;
  getItem<T>(collection: CollectionName, slug: string): Promise<T | null>;
  putItem<T extends { slug: string }>(collection: CollectionName, item: T): Promise<void>;
  deleteItem(collection: CollectionName, slug: string): Promise<void>;

  // Projects (keyed by a generated ID, not slug)
  listProjects(): Promise<Project[]>;
  putProject(project: Project): Promise<void>;
  deleteProject(id: string): Promise<void>;

  // Services (stored as a single list)
  getServices(): Promise<Service[]>;
  setServices(services: Service[]): Promise<void>;

  // Activity log
  appendActivity(entry: ActivityLogEntry): Promise<void>;
  queryActivity(opts: ActivityQueryOptions): Promise<ActivityLogEntry[]>;
}

export type CollectionName = "products" | "solutions" | "packages" | "insights";

export interface ActivityQueryOptions {
  limit?: number;
  since?: Date; // for 30-day metric aggregations
  eventTypes?: EventType[];
}
```

A D1 implementation (`D1ContentStore`) is the shipped default. A KV implementation (`KVContentStore`) can be swapped in via the adapter.

### 2. Auth_Service (`src/lib/auth.ts`)

Server-side module. Never imported by client bundles.

```ts
export async function login(
  username: string,
  password: string,
  ip: string,
  env: Env,
): Promise<
  | { success: true; sessionToken: string }
  | { success: false; reason: "invalid_credentials" | "rate_limited" }
>;

export async function logout(sessionToken: string, env: Env): Promise<void>;

export async function validateSession(
  sessionToken: string | undefined,
  env: Env,
): Promise<{ valid: true; username: string } | { valid: false }>;

export async function checkRateLimit(ip: string, env: Env): Promise<boolean>;
```

Session tokens are `crypto.randomUUID()` strings stored in KV with an 8-hour TTL. The KV key is `session:{token}` and the value is `{ username, createdAt }`. Rate-limit counters live in KV at `rl:{ip}:{window}` where `window` is `Math.floor(Date.now() / (15 * 60 * 1000))`.

Credentials (`ADMIN_USERNAME`, `ADMIN_PASSWORD_HASH`) are Cloudflare Worker secrets. Passwords are stored as bcrypt hashes (using the `bcryptjs` npm package which is pure JS and runs in the Workers runtime).

### 3. Content_API Server Functions (`src/api/`)

One file per content domain. Each file exports typed `createServerFn` calls.

```
src/api/
  auth.ts          — loginFn, logoutFn
  company.ts       — getCompanyFn, updateCompanyFn
  products.ts      — listProductsFn, upsertProductFn, deleteProductFn
  solutions.ts     — listSolutionsFn, upsertSolutionFn, deleteSolutionFn
  packages.ts      — listPackagesFn, upsertPackageFn, deletePackageFn
  projects.ts      — listProjectsFn, upsertProjectFn, deleteProjectFn
  insights.ts      — listInsightsFn, upsertInsightFn, deleteInsightFn
  services.ts      — getServicesFn, updateServicesFn
  activity.ts      — recordActivityFn, queryActivityFn
  upload.ts        — getUploadUrlFn
```

Every server function that mutates data validates its input with a Zod schema before writing to the store. Every server function under the admin domain calls `validateSession` from Auth_Service and throws a `redirect({ to: '/admin/login' })` if the session is invalid.

Example interface for products:

```ts
// src/api/products.ts
export const listProductsFn = createServerFn().handler(async ({ context }) => {
  const store = getContentStore(context.env);
  return store.listItems<Product>("products");
});

export const upsertProductFn = createServerFn()
  .validator(ProductSchema)
  .handler(async ({ data, context }) => {
    await requireAuth(context);
    const store = getContentStore(context.env);
    await store.putItem("products", data);
  });

export const deleteProductFn = createServerFn()
  .validator(z.object({ slug: z.string() }))
  .handler(async ({ data, context }) => {
    await requireAuth(context);
    const store = getContentStore(context.env);
    await store.deleteItem("products", data.slug);
  });
```

### 5. Admin Shell UI (`src/components/admin/`)

```
src/components/admin/

  AdminSidebar.tsx      — navigation links with active-link highlight

  ContentForm.tsx       — generic form wrapper with submit/cancel/delete
  DynamicList.tsx       — reorderable list field (highlights, specs, etc.)

  ConfirmDialog.tsx     — delete confirmation dialog (wraps Radix AlertDialog)
```

These components use the existing shadcn/ui primitives already in `src/components/ui/`. No new UI library is added.

### 6. Public Route Migration

Each existing public route loader is updated to call the corresponding server function instead of importing from `src/data/site.ts`:

```ts
// Before:
import { products } from "@/data/site";

// After:
export const Route = createFileRoute("/products/")({
  loader: () => listProductsFn(),
  component: ProductsPage,
});
```

`src/data/site.ts` is retained as a seed utility for the initial data migration script but is no longer imported by any runtime route.

### 7. Image Upload Flow

```
1. Admin selects file in ImageUpload component
2. Client validates: MIME type ∈ {image/jpeg, image/png, image/webp} AND size ≤ 5 MB
3. On valid file: call getUploadUrlFn({ filename, contentType }) [server function]
4. Server function calls R2.createMultipartUpload() or generates a presigned PUT URL
   and returns { uploadUrl, publicUrl }
5. Browser PUTs file bytes directly to R2 using uploadUrl (no Worker body limit hit)
6. On PUT 200: form field receives publicUrl value
7. On form submit: publicUrl is persisted in Content_Store alongside content item
```

### 8. Activity Recording

Public routes record events by calling `recordActivityFn` from their server-side handlers:

```ts
// In the products/$slug loader:
loader: async ({ params, context }) => {
  await recordActivityFn({
    type: "page_view",
    path: `/products/${params.slug}`,
    timestamp: new Date().toISOString(),
  });
  return getProductFn({ slug: params.slug });
};
```

`recordActivityFn` is fire-and-forget with error swallowing (requirement 2.7): if the write fails, the function logs to `console.error` and returns normally so the page render is not affected.

## Data Models

### D1 Schema

```sql
-- Content tables
CREATE TABLE company (
  id      INTEGER PRIMARY KEY DEFAULT 1,
  data    TEXT NOT NULL  -- JSON blob of Company object
);

CREATE TABLE products (
  slug      TEXT PRIMARY KEY,
  data      TEXT NOT NULL,  -- JSON blob of Product
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE solutions (
  slug      TEXT PRIMARY KEY,
  data      TEXT NOT NULL,
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE packages (
  slug      TEXT PRIMARY KEY,
  data      TEXT NOT NULL,
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE insights (
  slug      TEXT PRIMARY KEY,
  data      TEXT NOT NULL,
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE projects (
  id         TEXT PRIMARY KEY,  -- crypto.randomUUID()
  data       TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE services (
  id   INTEGER PRIMARY KEY DEFAULT 1,
  data TEXT NOT NULL  -- JSON array of Service objects
);

CREATE TABLE activity_log (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  event_type TEXT NOT NULL,
  path       TEXT,
  slug       TEXT,
  timestamp  TEXT NOT NULL  -- ISO 8601 UTC
);

CREATE INDEX idx_activity_timestamp ON activity_log(timestamp DESC);
CREATE INDEX idx_activity_type      ON activity_log(event_type);
```

JSON blobs are used for item data because the field shapes are complex (nested arrays, Spec_Entry pairs) and are always read/written as a unit. This avoids over-normalisation for a content type that does not need relational queries within a single item.

## Correctness Properties

_A property is a characteristic or behavior that should hold true across all valid executions of a system — essentially, a formal statement about what the system should do. Properties serve as the bridge between human-readable specifications and machine-verifiable correctness guarantees._

### Property 1: Unauthenticated requests to any admin route are redirected

_For any_ path that begins with `/admin` (excluding `/admin/login` itself), a request carrying no session cookie or an invalid session token SHALL receive a redirect response to `/admin/login` — regardless of which specific admin route is targeted.

**Validates: Requirements 1.1, 1.6**

---

### Property 2: Invalid credentials never reveal which field is wrong

_For any_ (username, password) pair that does not exactly match the stored admin credentials, the Auth_Service response SHALL not contain the strings `"username"`, `"password"`, or any phrase indicating which specific field failed. The same generic error message SHALL be returned whether the username is wrong, the password is wrong, or both are wrong.

**Validates: Requirements 1.3**

---

### Property 3: Content round-trip — write then read returns identical data

_For any_ valid content item (Product, Solution, Package, Insight, Service item, or Company_Info), submitting that item through the corresponding server function SHALL result in the Content_Store returning an identical value on the next read of that item. No field may be silently dropped, truncated, or transformed.

**Validates: Requirements 3.2, 4.3, 4.5, 5.3, 5.5, 6.3, 6.5, 7.3, 7.5, 8.3, 8.5, 9.2**

---

### Property 4: Slug uniqueness is enforced across each collection independently

_For any_ collection (products, solutions, packages, insights), if a slug `S` already exists in that collection, attempting to add a different item with the same slug `S` SHALL be rejected with a duplicate-slug error. The rejection SHALL apply regardless of the other fields of the new item.

**Validates: Requirements 4.8, 5.8, 6.8, 8.8**

---

### Property 5: Required-field validation rejects any form with a blank required field

_For any_ content form, and for any assignment of values where at least one required field (as defined per content type) is empty or contains only whitespace, the form submission SHALL be rejected and a validation error SHALL be reported on each offending field. The set of required fields is:

- Company: `name`, `email`, `whatsappHref`
- Product: `slug`, `name`, `category`, `summary`
- Solution: `slug`, `name`, `summary`
- Package: `slug`, `name`
- Project: `title`, `copy`
- Insight: `slug`, `title`, `copy`
- Service item: `title`, `copy`

**Validates: Requirements 3.3, 4.7, 5.7, 6.7, 7.7, 8.7, 9.5**

---

### Property 6: Email field rejects all non-RFC-5322 strings

_For any_ string that is not a syntactically valid RFC 5322 email address, the `email` validator SHALL reject it and surface a field-level error. Valid email addresses SHALL pass the same validator without error.

**Validates: Requirements 3.4**

---

### Property 7: Activity log entries faithfully record their inputs

_For any_ event type and associated metadata (path, slug, timestamp), a call to `recordActivityFn` SHALL result in an `ActivityLogEntry` stored in the Content_Store whose `eventType`, `path`, `slug`, and `timestamp` fields exactly match the inputs provided.

**Validates: Requirements 2.3, 2.4, 2.6**

---

### Property 8: Dashboard "recent 10" shows the newest entries and no others

_For any_ activity log containing N entries (N ≥ 1), the dashboard list SHALL contain exactly `min(N, 10)` entries, and those entries SHALL be the `min(N, 10)` entries with the most recent timestamps. No entry with an older timestamp than the 10th-most-recent SHALL appear in the list.

**Validates: Requirements 2.2**

---

### Property 9: Image upload rejects any file outside the allowed type or size envelope

_For any_ file where MIME type ∉ {`image/jpeg`, `image/png`, `image/webp`} OR whose byte size > 5,242,880 (5 MB), the ImageUpload component SHALL reject the file before making any network request, and no upload to R2 SHALL occur.

**Validates: Requirements 10.2, 10.4, 10.5**

---

### Property 10: Public pages reflect Content_Store state on the very next request

_For any_ content type that is updated via the Content_API, the next server-rendered HTTP request to any public page that displays that content type SHALL return a response reflecting the updated state. No cached version of the previous state SHALL be served.

**Validates: Requirements 3.5, 4.10**

---

### Property 11: ISO 8601 date validation rejects all non-YYYY-MM-DD strings

_For any_ string that is not of the form `YYYY-MM-DD` (four-digit year, valid month 01–12, valid day 01–31), the date field validator SHALL reject it. Valid `YYYY-MM-DD` strings SHALL pass.

**Validates: Requirements 7.8**

## Error Handling

### Authentication Errors

| Scenario                            | Behaviour                                                      |
| ----------------------------------- | -------------------------------------------------------------- |
| Missing session cookie              | Redirect to `/admin/login`; no 401 exposed to client           |
| Expired session token               | KV TTL expiry causes lookup miss → same redirect               |
| Tampered session token              | Lookup miss in KV → redirect                                   |
| Rate limit exceeded (>10 in 15 min) | HTTP 429 with `Retry-After` header; no error detail leaked     |
| Invalid credentials                 | Generic error: "Incorrect username or password"; no field hint |

### Content_API Errors

| Scenario                         | Behaviour                                                         |
| -------------------------------- | ----------------------------------------------------------------- |
| Zod validation failure           | Return `{ success: false, errors: ZodError.flatten() }` to client |
| Duplicate slug                   | Return `{ success: false, errors: { slug: 'already in use' } }`   |
| D1 write failure                 | Log server-side; return HTTP 500 with generic message             |
| R2 upload URL generation failure | Return HTTP 500; client shows "Image upload unavailable" toast    |

### Activity Log Errors (Requirement 2.7)

`recordActivityFn` wraps its D1 write in a try/catch. On failure it calls `console.error(err)` and returns `{ ok: true }` so the calling loader is unaffected. This ensures activity recording failures are never surfaced to visitors.

### Public Site Errors

If a public-route loader cannot reach the Content_Store (D1 unavailable), TanStack Router's `errorComponent` renders the existing error page. This is the same behaviour as today's unhandled server errors (already handled in `src/server.ts`).

## Testing Strategy

### Unit Tests (Vitest)

Scope: pure logic — Zod validators, slug normalisation, date parsing, Auth_Service token operations, activity query filtering.

Focus areas:

- All Zod schemas: valid inputs pass, invalid inputs produce expected error shapes
- `checkRateLimit`: boundary at 10 requests, reset after window
- `validateSession`: valid token returns user, expired/missing token returns `{ valid: false }`
- Activity query filter: `since`, `limit`, and `eventTypes` parameters applied correctly
- `DynamicList` component: add/remove/reorder operations update state correctly

Avoid writing unit tests for things property tests already cover exhaustively. Keep unit tests focused on concrete examples and error scenarios.

### Property-Based Tests (fast-check, Vitest)

Each property in the Correctness Properties section above maps to one property-based test. Tests run via Vitest with `fc` (fast-check) configured to a minimum of **100 runs** per property.

```ts
// Example: Property 3 — Content round-trip
it.prop([fc.record({ slug: fc.slug(), name: fc.string({ minLength: 1 }), ... })])(
  'Feature: admin-panel, Property 3: content round-trip preserves all fields',
  async (product) => {
    await store.putItem('products', product);
    const retrieved = await store.getItem('products', product.slug);
    expect(retrieved).toEqual(product);
  }
);
```

Tag format: `Feature: admin-panel, Property {N}: {property_text}`

Each property test is tagged with a comment referencing the design property it validates.

### Integration Tests

Manual or scripted against a local `wrangler dev` environment with a local D1/KV instance:

- Login → session cookie → access protected route → success
- Login with wrong password N times → 11th attempt → HTTP 429
- Create product → visit `/products` → product appears
- Update company name → visit `/` → new name in page
- Upload image → R2 object created → URL stored in content item

### Smoke Tests

Single-run checks against the deployed Worker:

- `/admin` redirects to `/admin/login` (no session)
- `/admin/login` returns 200
- D1 binding is present (`wrangler d1 info`)
- KV namespace is present (`wrangler kv namespace list`)
- R2 bucket is accessible
